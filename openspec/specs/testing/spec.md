# Testing

## Purpose

Testing covers the coverage gates per module, why the `spring` packages sit outside them, the wire-assertion
approach for the S3 adapter, why no test reaches a live bucket, and why every recognised format is tested from real
bytes rather than from the constants the sniffer was written from.

## Requirements

### Requirement: Coverage is gated per module at 90% line and 80% branch
Coverage SHALL be gated PER MODULE at 90% line and 80% branch, never merged across modules. `storage-core`'s gate
SHALL cover `net/aetherealtech/storage/*`, `upload/*` and `tx/*`; `storage-s3`'s gate SHALL cover
`net/aetherealtech/storage/s3/*`.

#### Scenario: Each module has its own coverage gate
- **WHEN** the build runs coverage checks
- **THEN** `storage-core` and `storage-s3` are each gated separately at 90% line and 80% branch
- **AND** no merged, cross-module figure is used to pass either gate

### Requirement: The spring packages sit outside the coverage gate
The `spring` packages in both modules SHALL sit outside their module's coverage gate. What they must get right —
which `ObjectStorage` a given mode and set of credentials produces — SHALL instead be proven by the decision
matrices in the autoconfiguration tests, rather than by a percentage over accessors that exist only for Spring's
binder to call.

#### Scenario: spring packages are excluded from the gate but covered by a decision-matrix test
- **WHEN** `net.aetherealtech.storage.spring` or `net.aetherealtech.storage.s3.spring` is inspected for coverage
- **THEN** it sits outside the module's JaCoCo gate
- **AND** its correctness is instead asserted by the autoconfiguration tests' decision matrices

### Requirement: The S3 tier asserts the actual wire, never a round trip
`S3ObjectStorageTest` SHALL assert the actual HTTP the AWS SDK puts on a socket — the `Host` header virtual-hosted
addressing produces, the request line path-style produces, the PUT body, and the SigV4 query parameters on a
presigned URL — against WireMock. A test that writes with `S3ObjectStorage` and reads it back with the same
`S3ObjectStorage` SHALL NOT be relied on alone, since it would only prove the adapter agrees with itself, not what
an S3-compatible store will actually accept.

#### Scenario: A wire test asserts the Host header and PUT body against WireMock
- **WHEN** `S3ObjectStorageTest` runs
- **THEN** it asserts the actual `Host` header, request line, PUT body and presigned-URL query parameters against
  WireMock, not merely a write followed by a read through the same adapter

### Requirement: No test reaches a live bucket, needs Docker, or needs MinIO
No test SHALL reach a real bucket, and no test SHALL need Docker or MinIO. A suite that needs credentials is a suite
that quietly stops running.

#### Scenario: The full test suite runs with no bucket, no Docker and no MinIO
- **WHEN** `./mvnw clean verify` runs
- **THEN** no test connects to a real object-storage bucket
- **AND** no test requires Docker or MinIO to be running

### Requirement: Every recognised format is tested from real bytes
Every recognised format SHALL be tested from REAL bytes — ImageIO-generated for PNG and JPEG, hand-written headers
for the rest. A sniffer tested against the constants it was written from tests nothing.

#### Scenario: PNG and JPEG are tested against ImageIO-generated bytes
- **WHEN** the PNG and JPEG signature checks are tested
- **THEN** the test bytes are produced by `ImageIO`, not copied from the signature constants themselves

#### Scenario: Other formats are tested against hand-written headers
- **WHEN** GIF, WEBP, BMP, TIFF, PDF, HEIC or AVIF signature checks are tested
- **THEN** the test bytes are hand-written headers matching real files of that format, not the signature constants
